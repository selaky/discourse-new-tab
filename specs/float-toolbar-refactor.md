# 悬浮工具栏改造需求文档

## 📋 项目概述

### 背景
当前脚本拥有一个悬浮球功能，作为后台打开功能的附属品，仅用于快速切换后台打开模式。现需将其改造为独立的悬浮工具栏，增加更多功能，并为未来扩展打下良好的框架基础。

### 目标
1. 将悬浮球改造为竖排悬浮工具栏
2. 增加"回到顶部"和"打开设置"两个新功能按钮
3. 将悬浮工具栏从后台打开功能中分离，作为独立板块
4. 提供完整的设置界面，支持功能开关、排序和位置管理
5. 为未来的动态显示功能预留扩展性

### 核心原则
- **保持用户体验**：在维持原有体验基础上进行改进，避免大幅改动
- **一次点击达成目标**：竖排直接显示所有开启功能，无需展开菜单
- **模块化设计**：功能项可独立管理、配置和扩展
- **扩展性优先**：为未来的动态显示、条件判断等功能预留架构空间

### 可复用的核心能力

#### 1. 定位与拖拽系统 ✅
- 基于视口百分比的位置存储机制（xRatio, yRatio）
- 拖拽阈值防误触逻辑（5像素）
- 边界限制和响应式定位
- requestAnimationFrame 性能优化
- **评估**：成熟稳定，可直接复用于工具栏

#### 2. 主题适配系统 ✅
- 跟随设置面板的主题切换（light/dark/auto）
- 自动检测系统主题
- **评估**：可直接复用

#### 3. 存储架构 ✅
- GM_setValue/GM_getValue 持久化存储
- 跨页面同步机制（gmOnValueChange）
- **评估**：数据结构需扩展，但底层机制可复用

#### 4. 样式基础 ✅
- 毛玻璃效果（backdrop-filter）
- 动画和过渡效果
- **评估**：可作为工具栏样式的基础

### 需要重构的部分

#### 1. 功能耦合问题 ⚠️
- 当前悬浮球与后台打开功能强耦合
- 点击事件直接调用 `cycleMode()`
- **问题**：无法容纳多个独立功能按钮
- **方案**：解耦模式切换，将其作为工具栏的一个功能项

#### 2. 单一交互模式 ⚠️
- 当前只支持"点击整个球体"一种交互
- **问题**：无法实现竖排多按钮布局
- **方案**：重构为容器+多按钮的架构

#### 3. 设置界面结构 ⚠️
- 悬浮球设置嵌套在"后台打开"分类中
- **问题**：不符合独立板块定位
- **方案**：拆分设置界面，重新组织层级

#### 4. 功能扩展能力 ⚠️
- 当前架构仅为单一功能设计
- 缺乏功能项的抽象和管理机制
- **问题**：难以支持动态显示/隐藏、条件判断等特性
- **方案**：设计功能注册系统，支持元数据配置

## 📝 详细需求

### 功能需求

#### 1. 工具栏基础功能
- **竖排布局**：所有开启的功能按钮竖排显示
- **默认功能**：回到顶部、模式切换、打开设置（按此顺序）
- **总开关**：可通过设置界面完全关闭工具栏
- **定位系统**：
  - 支持自由拖拽调整位置
  - 位置以视口百分比存储，响应式适配
  - 默认位置：右下角
- **拖拽手柄**：
  - 专门的拖拽把手按钮/区域
  - 可在设置界面关闭拖拽功能（固定位置）
  - 固定模式下隐藏拖拽手柄
- **主题适配**：跟随设置界面主题自动切换

#### 2. 功能按钮

##### 按钮1：回到顶部
- **功能**：点击后页面滚动到顶部
- **默认状态**：开启
- **默认顺序**：1

##### 按钮2：模式切换
- **功能**：循环切换后台打开模式（none → topic → all）
- **交互方式**：点击循环切换
- **视觉反馈**：显示当前模式状态（复用原有逻辑）
- **可配置**：在设置中选择可切换的模式（至少2个）
- **默认状态**：开启
- **默认顺序**：2

##### 按钮3：打开设置
- **功能**：点击打开脚本设置界面
- **默认状态**：开启
- **默认顺序**：3

#### 3. 设置界面

##### 新建"悬浮工具栏"分类
独立的设置分类，包含以下内容：

**基础设置**
- 显示悬浮工具栏（总开关）
- 固定位置（禁用拖拽）
- 重置位置按钮

**功能管理**
- 功能列表展示（每个功能一行）
- 每个功能项包含：
  - 启用开关
  - 功能名称和描述
  - 拖拽手柄（用于排序）
- 拖拽排序交互
- 重置功能配置按钮（恢复默认开关状态和排序）

**模式切换专属设置**（仅在模式切换功能开启时显示）
- 可切换模式选择器（从原后台打开设置迁移）
- 至少选择2个模式

##### 调整"跳转规则"分类
- 将"当前后台打开模式选择器"移到该分类顶部
- 说明：从逻辑上，后台打开模式属于跳转规则，工具栏仅为其快捷操作入口

##### 调整"后台打开"分类
- 移除该分类,内容拆分移动到其他分类.原打开方式设置移动至跳转规则,原悬浮球设置移动至悬浮工具栏.

### 非功能需求

#### 1. 性能要求
- 拖拽操作流畅，无明显卡顿
- 按钮点击响应及时（<100ms）
- 工具栏渲染不影响页面加载速度

#### 2. 兼容性要求
- 支持 Tampermonkey / Violentmonkey / Greasemonkey
- 兼容主流浏览器（Chrome、Firefox、Edge）
- 适配不同屏幕尺寸（响应式设计）

#### 3. 可维护性要求
- 代码模块化，职责清晰
- 功能项注册机制，便于添加新功能
- 配置数据结构化，便于扩展

#### 4. 扩展性要求（架构预留）
- 支持未来添加动态显示条件
  - 页面类型判断（复用现有接口）
  - 自定义 URL 匹配
  - 其他条件（登录状态、特定论坛等）
- 支持为每个功能配置显示条件
- 条件判断引擎预留接口

│  - 拖拽手柄渲染与交互                │

└─────────────────────────────────────┘
           ↓ 管理
┌─────────────────────────────────────┐
│  ActionRegistry (功能注册中心)       │
│  职责：                              │
│  - 功能项注册与查询                  │
│  - 功能启用状态管理                  │

│  - 条件判断引擎（预留接口）          │

           ↓ 渲染

## 🔧 技术要点与注意事项

### 数据迁移策略

**决策**：不考虑老用户迁移

**原因**：
- 架构差异较大，迁移成本高
- 旧悬浮球设置较少,且只存在于一个小版本,用户可通过设置重新配置

**实施**：
- 使用新的存储键名
- 旧数据不保留
- 首次加载使用默认配置

### 扩展性设计原则

#### 1. 开闭原则
- 核心代码对修改封闭，对扩展开放
- 添加新功能无需改动 core.ts 和 registry.ts

#### 2. 单一职责
- 每个模块职责明确,例如:
- ActionButton 只负责渲染和事件
- ActionRegistry 只负责管理和配置
- FloatToolbar 只负责容器和布局

#### 3. 依赖倒置
- 功能项依赖抽象接口（ActionDefinition）
- 核心模块不依赖具体功能实现

#### 4. 接口隔离
- 条件判断接口独立
- 设置渲染接口独立
- 不强制功能项实现所有接口
